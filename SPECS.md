# SPECS.md - step specifications for the pipeline

*What this is:* the step-by-step specification behind DESIGN.md › 1. Pipeline. DESIGN.md explains each phase; this file says, per step, what it does, how, and a worked example from the Vestas Annual Report 2025. Step numbers (E, T, L) are shared with DESIGN.md, the run record and the stage reports.

## EXTRACT

| # | Step | What | How | Example |
| --- | --- | --- | --- | --- |
| E1 | TOC links | The table of contents in an InDesign export carries one link annotation per entry, and the PDF resolves each to a page index. Read the TOC pages (those with 5 or more dotted "Title …… 123" lines among the first dozen pages), pair every link with the entry text on its line, and keep title → page index. The printed number is kept alongside for provenance. Fallback for a PDF without links: the dotted entries give printed numbers, and the footer number (bottom-right, right-most small number) gives the offset to PDF indices, voted across sections | PyMuPDF `get_links()`, words on the link's line; fallback: footer words | p.2 has 64 links; the "Risk management ···· 50" line resolves to index 49, "Material impacts, risks, and opportunities ···· 71" to 70, "Climate change ···· 85" to 84, "Cyber security (entity-specific) ···· 118" to 117 |
| E2 | Match titles | The section-title vocabulary (seeded with the brief's four; exact and variant matches join as synonyms, similarity matches only after review) against every normalised TOC title. Normalisation: lowercase, unify dashes and quotes, drop parenthetical qualifiers, drop punctuation, collapse whitespace. Three grades: exact (1.0); variant (one string starts with the other plus a space, 0.95); similarity (longest-common-subsequence ratio), accepted at 0.85 or above. Best entry wins. Section end = the next TOC entry's page minus one, capped by the configured range | string normalisation, prefix test, similarity ratio | "cyber security" vs "cyber security" after the qualifier is dropped → exact, reported as a variant of the printed title; "risk management" vs "risk management and internal control" → 0.95; "material impacts risks and opportunities" vs "impacts risks and opportunities" → 0.87; "risk management" vs "risk factors" → 0.52, no match; Risk management runs 50–51 because the next entry is at 52 |
| E3 | Validate sections | The validation point for a new report, per expected section. Match grade: exact or variant → ok; similarity → warning, the new title queued for review; no match → error if required (Risk management; Material impacts, risks, and opportunities), warning if optional (Climate change; Cyber security). Landing page: the normalised title must appear on the page the link points to, and the footer number must equal the printed number; either failing is an error for a required section, a warning for an optional one. An error stops the run for that report and marks it deferred (PLAN.md › Assumptions). Every outcome is counted on the run record (L6). Never a silent skip | rule table: grade × required/optional; text search on the landing page | "Cybersecurity" for "Cyber security" → 0.96 → warning, queued; "Enterprise risk management" for "Risk management" → 0.73 → error, report deferred; index 49 contains "risk management" and footer "50" → ok; on a copy with a blank page inserted at the front the link still resolves to the right index and the footer still reads "50" → ok |
| E4 | Read the section content | Each located page as words with x/y box, font name and size, plus the page's horizontal rules and vector drawings; footer band dropped; words grouped into lines by vertical tolerance, top-down and left-to-right. No interpretation yet | PyMuPDF `get_text("dict")`, `get_drawings()`; y-tolerance clustering | on p.51, "Cyber" and "attacks" sit at the same height (top ≈ 98 pt) → one line; a word in the bottom 28 pt is footer → dropped |
| E5 | Main-risks table (p.51) | Large-font words are headings: left margin → row labels (Description / Potential impact / How we manage it), right → column heads (the three risks), clustered by horizontal gaps; each body word is assigned to its (column, row) cell by coordinates and the text is rebuilt per cell in reading order. Parser chosen by printed page number. Plain text order scrambles this table, and neither PyMuPDF's table finder nor pymupdf4llm recovers the third column | word coordinates, font size | "Cyber attacks" (size 12, x ≈ 627) → column 3 head; "Description" (size 12, x ≈ 34) → row 1 label; a size-7 word at x ≈ 640, top ≈ 200 → cell (column 3, Description) |
| E6 | ESRS tables (pp.71–74) | ESRS: the European Sustainability Reporting Standards, under which the sustainability statement lists material impacts, risks and opportunities per topic (E1 climate change … G1 business conduct). One table per "Sub-topic" header; topic code from the heading above; column positions from the header words; rows = spans between horizontal rules per column; entries split at name lines (Medium font) vs description lines; value chain from its column. **Risk vs opportunity** has three sources, in order: the arrow icon in the vector drawings (apex above the shaft = up = opportunity, below = risk); the row text ("presents a financial opportunity" vs "pose a financial risk", "increase the cost"); and the topical section's own "Type of impact: Financial risk / Financial opportunity" line for the same IRO name (the report states it 28 times). Icon and row text are both read here and must agree; disagreement or a missing icon is flagged, and the topical line settles it in T5 enrichment | word coordinates, font weight, page rules and drawings, text rule | G1 financial column, the row between two rules: "Cyber security risks" in Medium, "Cyber attacks might disrupt…" in Standard; icon down → risk; text says "risks" → agree; p.118 says "Type of impact: Risk" → third agreement. "Low-emission materials": icon up, text "presents a financial opportunity", climate section "Type of impact: Financial opportunity" → opportunity |
| E7 | Persist | Blocks with section, printed page, PDF index, register, ESRS topic code, sub-topic, marker and its sources, value chain, flags, and the strategy that produced each block (table parser or plain text); pages without a table parser (p.50, pp.85–92, p.118) as one plain-text block each, flagged as not layout-reconstructed | typed models → per-run files | block "Cyber security risks", section Material impacts, page 74, register ESRS financial risk, code G1, sub-topic Cyber security, marker risk (icon and text), value chain Own operations, strategy table parser |
| E8 | Validate the extraction | End-of-phase checks, error or warning by the required/optional rule, counted on the run record: every located section produced at least one block; the main-risks table has 3 columns × 3 rows with no empty cell; every ESRS financial row has a marker, and the count of marker disagreements is reported; every block's text is a substring of its page's text (nothing invented, nothing moved across pages); the words in a page's blocks cover at least 95% of the page's non-footer words (nothing dropped); block ids are unique and pages lie inside their section range; counts compared with the previous run of the same report, a change is a warning | deterministic checks on the persisted blocks | p.51 → 3 × 3 cells, all non-empty → ok; pp.71–74 → 7 risk rows, 3 opportunity rows, 0 marker disagreements → ok; a page whose blocks cover 80% of its words → warning |

## TRANSFORM

| # | Step | What | How | Example |
| --- | --- | --- | --- | --- |
| T1 | Identify | Candidate risks with verbatim spans. Two strategies, both run: from the report's own registers (the p.51 columns and the ESRS rows marked as risks) and from the section text (an LLM proposes candidates against a written definition of a principal risk, each with a verbatim span that must exist on the page). The register result takes precedence; the agreement between the two is recorded, which is what a report without a register would lose | table rows; LLM structured output; span check | register → "Cyber attacks", p.51; LLM → span starting "Vestas' digital and other critical assets are exposed to cyber attacks", p.51 → same risk, agreement recorded |
| T2 | Describe and categorise | One LLM call per risk returns the record's model-written fields together: a 2–3 sentence description, the primary category and any secondary categories, and the mitigation as stated or null. Categories are the brief's seven and stay sector-neutral; the report supplies the mapping rule and its worked examples, never new categories; a risk that fits poorly gets a poor-fit flag, and the count of those is the evidence for extending the taxonomy later. The ESRS topic code narrows the candidate categories where it exists; when category confidence is low, N samples are drawn and the majority wins | structured output constrained by the record schema, temperature 0, versioned prompt, every call recorded for replay; ESRS-code prior; majority vote | "Cost implication of injuries in own workforce" → operational (cause: workplace injuries), not financial (consequence); "Carbon taxes and tariffs" (E1) → candidates climate or regulatory → regulatory primary, climate secondary |
| T3 | Merge | Same risk in two registers → one record, all citations | fuzzy title match; embeddings later | "Cyber attacks" (p.51) and "Cyber security risks" (p.74, G1) → one record with two citations |
| T4 | Validate and repair | Per record: schema, page range, category enum, sentence count; grounding: the span must be a substring of the page text; each description sentence must share enough content words with the span, and any number, year or capitalised name in it must occur in the span; mitigation must match the "how we manage it" text or be null where the span states none | typed validation, sentence split, fuzzy overlap; one retry with the error attached, then quality flags | a description sentence mentioning "SCADA" fails, the word is not in the p.51 span; a mitigation of null for "Fines related to forced or child labour" passes, the ESRS row states none |
| T5 | Enrich (optional) | Entities; model-independent category check; the topical section's "Type of impact" line as the third source for risk vs opportunity (E6) | spaCy NER; sentence-embedding similarity to category prototypes; text search in the topical section for the IRO name | "Geopolitics and regulatory framework" → entities EU, China, USA, Ukraine, Middle East |
| T6 | Validate the transform | End-of-phase checks on the whole record set, counted on the run record: record count equals candidates minus merges; every record has at least one citation whose span exists on its page; canonical ids are unique and a merged risk appears once with all its citations; every record has a primary category from the enum; identification agreement between the two T1 strategies and the grounding pass rate are above their thresholds, otherwise a warning; a replay of the recorded calls reproduces the record set exactly (determinism); for a report with a golden set, the five evaluators run here (identification precision and recall, provenance, grounding, category agreement, field presence) and a failing evaluator is an error that stops the load; record count compared with the previous run of the same report, a change is a warning | deterministic checks; evaluators in replay mode | 10 candidates, 1 merge → 9 records → ok; cyber once with 2 citations → ok; agreement 9/9, grounding 9/9, replay identical → ok; evaluators 5/5 → load proceeds |

## API

| # | Step | What | How | Example |
| --- | --- | --- | --- | --- |
| A1 | Open | Attach the SQLite file read-only; check its schema version against the one the service was built with; refuse to start on a mismatch | SQLite URI `mode=ro`; version row in the database | database written by pipeline 0.1 → service 0.1 → ok; 0.2 → refuse with the two versions in the error |

| A3 | Parse question | One structured-output call, question → intent (categories, companies, years, register, status, leftover text); same taxonomy and mapping rule as T2; call recorded for replay | structured output constrained by the intent schema, temperature 0, versioned prompt | "which renewable-energy companies list cyber security as a principal risk" → categories [cyber], register any, sector renewable energy, leftover "" |
| A4 | Run intent | Intent → the same SQL as A2; leftover text → FTS5 over title and description, BM25-ranked, intersected with the filters | SQL + FTS5 MATCH | leftover "tariffs" → matches "Geopolitics and regulatory framework" and "Carbon taxes and tariffs" |

## Validation points

| Check | Phase | What it verifies | How | Severity | Run-record field | A failure points at |
|---|---|---|---|---|---|---|
| E3 match | EXTRACT | configured title matched exact, variant, similarity or not at all | normalised string equality, prefix test, longest-common-subsequence ratio with a 0.85 floor | similarity: warning; none: error if required, warning if optional | `section_match_grade` | the title vocabulary |
| E3 landing | EXTRACT | title present on the landing page and footer equals the printed number | normalised substring search in the page text; right-most small number in the footer band | error if required, warning if optional | `landing_page_ok` | TOC links or page mapping |
| E8 blocks | EXTRACT | every located section produced at least one block | count of blocks per section in the persisted output | error if required, warning if optional | `blocks_per_section` | the page parser for that layout |
| E8 shape | EXTRACT | main-risks table is 3 × 3 with no empty cell | count column heads and row labels; every cell text non-empty | error | `main_risks_shape` | the p.51 parser |
| E8 marker | EXTRACT | every ESRS financial row has a marker; icon and text agree | icon direction from the arrow path vs the row-text rule, compared per row | missing: warning; disagreements counted | `marker_missing`, `marker_disagreement` | icon reading or the text rule |
| E8 fidelity | EXTRACT | every block's text is a substring of its page | whitespace-normalised substring test against the page's plain text | error | `text_not_on_page` | line grouping, cross-page bleed |
| E8 coverage | EXTRACT | blocks cover at least 95% of a page's non-footer words | word multiset of the page's blocks divided by the page's word multiset | warning | `page_coverage` | a parser dropping content |
| E8 drift | EXTRACT | counts equal the previous run of the same report | compare block counts per marker and page with the last run record for the report | warning | `count_drift` | a parser regression |
| T1 agreement | TRANSFORM | register candidates vs model-proposed candidates | fuzzy title match between the two candidate sets; agreement = matched ÷ register count | below threshold: warning | `identify_agreement` | the register assumption |
| T2 poor fit | TRANSFORM | risks flagged as fitting no category well | the poor-fit flag returned in the structured output, counted per run | counted | `category_poor_fit` | the taxonomy |
| T4 schema | TRANSFORM | schema, page range, category enum, sentence count | Pydantic validation; page inside the section range; enum membership; sentence split and count | one retry, then flag | `record_schema_failures` | the prompt |
| T4 grounding | TRANSFORM | span on page; sentences share content with the span; numbers and names in the span; mitigation matches or is null | substring test for the span; content-word overlap per sentence above a floor; regex for numbers, years and capitalised names checked against the span; fuzzy match of the mitigation to the "how we manage it" text | one retry, then flag; rate below threshold: warning | `grounding_failures` | the model or the prompt |
| T6 set | TRANSFORM | record count, unique canonical ids, citations exist, categories in enum | count = candidates − merges; id uniqueness; every citation's span found on its page; enum membership | error | `transform_set_checks` | merge or identify |
| T6 replay | TRANSFORM | replaying recorded calls reproduces the record set | rerun the phase with `--replay` and compare the serialised record set byte for byte | error | `replay_identical` | provider nondeterminism |
| T6 evaluators | TRANSFORM | the five evaluators against the golden set | identification precision and recall, exact page and section, key-phrase grounding, category agreement, field presence, each against `golden.json` | failing evaluator: error, stops the load | `eval_scores` | parser (identification, grounding), model (category), prompt (field presence) |
| A1 version | API | database schema version equals the service's | read the version row at start-up and compare with the service constant | refuse to start | `api_schema_version` | deployment |
| A3 intent | API | question golden set: category and filter agreement | run the recorded intent calls against the question golden set; compare categories and filters field by field | below threshold: warning | `intent_agreement` | the intent prompt or the mapping rule |

## Run record

Two tables, written by every phase and by the API.

`run`: `run_id`, `report_id`, `pdf`, `model`, `prompt_version`, `phases`, `started_at`, `finished_at`, `status` (ok, warnings, error, deferred).

`run_record`: one row per (run, report, check): `run_id`, `report_id`, `phase`, `check_id` (from the table above), `outcome` (ok, warning, error), `count`, `strategy` (which parser or match grade produced the result), `detail` (JSON: the flagged items), `created_at`.

Reading it: one query per check across reports gives the failure rate per step; the "points at" column turns that rate into the next task.
